> WARNO / Eugen Systems 系游戏 Mod 数据的**知识库 + 工具集**，以 WorkBuddy Skill 形式交付。  
> 一句话目标：把「这个能不能做」变成「改这里、填这个、注意这个」。

| 项    | 值                                                                                         |
| ---- | ----------------------------------------------------------------------------------------- |
| 形态   | WorkBuddy Skill。**不是** mod 工程，**不是**可运行的编辑器程序                                             |
| 体量   | 1 个入口 `SKILL.md`（215 行）+ 14 份 `references/`（5,743 行）+ 20 个 `scripts/`（6,559 行），共 12,517 行 |
| 知识来源 | WARNO 官方 Mods `base.zip`（4,564 个 `.ndf`）、`WARNO.exe` RTTI 类型表、崩溃转储、**实机验证**               |
| 覆盖   | 只读勘查 / 造单位·弹药·外观 / 自定义网格与可动部件 / 将军模式(AG) / 行为层 / 游戏 UI / 数值语义 / 编译与崩溃分诊                   |
| 仓库   | Git 仓库，`main` 分支，首次提交 `1399787`                                                           |

## 0. 边界：是什么、不是什么

**管**：WARNO 官方 Mods 目录里 4500+ 个 `.ndf` 的勘查、改写与验收，以及配套的模型 / 贴图 / 动画资产接入。  
产出物是「要开发某编辑器 → 改哪些文件 → 字段怎么填 → 有哪些枚举 → 有什么坑」的支撑报告，外加可复用的脚本。

**不管**：

- **写编辑器界面**（WinForms / PySide / Qt 的窗口与交互）→ 走 `eugen-ndf-editor-pattern`。  
  注意这里最容易混：**改游戏里的 UI**（图标、配色、HUD、AG 面板、兵牌）是本仓库 `70-ui.md` 与 `20-unit-authoring.md §2.5` 的事；**做一个改数据的桌面编辑器**才归 editor-pattern。
- 别的 Eugen 游戏（Steel Division 2 / Wargame Red Dragon）→ 数据结构不同，不要套用。
- mod 本体、游戏安装工程与发布流程 → 本仓库只提供数据知识与工具，不含可直接编译的完整 mod 工程。

## 1. 权威性与阅读顺序

**冲突时以 `SKILL.md` 为准。** 本 README 只是导读与仓库约定，刻意不复制知识正文，避免两份内容失同步。

| 层级       | 文件                | 职责                               | 什么时候读                   |
| -------- | ----------------- | -------------------------------- | ----------------------- |
| L0 权威入口  | `SKILL.md`        | 查 / 改判据、任务路由表、13 条全局铁律、能力边界速答、索引 | **每次任务开始**，先读这一份        |
| L1 知识正文  | `references/*.md` | 按任务线拆开的原理、字段表、实测记录、排错            | 由 `SKILL.md §2` 路由命中后再读 |
| L2 可执行工具 | `scripts/*.py`    | 勘查、克隆、模型体检、编译守卫、验收渲染             | 由对应 reference 指定调用      |
| 导读（本文件）  | `README.md`       | 仓库结构、运行约定、给智能体的执行清单、参数总表         | 首次接手 / 需要查环境约定时         |

主文件采用**渐进披露**：`SKILL.md` 只做「分流 + 立规矩 + 给索引」，任何「怎么做」都不进主文件。  
需要细节时按路由精确加载一份 reference，而不是把 14 份全读进上下文。

### 4.2 Blender 脚本（9 个）— 必须用 `blender -b -P`，参数写在 `--` 之后

| 脚本                    | 用途                                                                                                                |
| --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `mesh_check.py`       | 模型体检（只读）：顶点数、UV 范围、焊接后壳数、边界边比例、锚点坐标；**`--cook`** 预检 AssetCooker 门槛（退化面 / 零法线 / n-gon / ORM 走 MATH 中转），`rc=1` 即有硬伤 |
| `split_shells.py`     | 三角汤拆件：焊接 → 连通块 → 整壳归组 → 按 AABB 拆成独立节点 → 导出 FBX                                                                    |
| `split_wheels.py`     | ⭐ 拆轮：双判据并集（轮材质 ∪ 圆盘几何）→ `roue_elev_*` 空物体 + 子网格，强制 `matrix_parent_inverse = Identity`；只按材质筛会漏诱导轮                  |
| `track_uv_axis.py`    | 履带 UV 走向轴判定（只读），与官方 M1 对照                                                                                         |
| `pick_anchor.py`      | ⭐ 锚点定位四合一：`render` 渲同角度图并叠 A–T / 1–16 网格，`pick` 把**格子**（如 `M8`）反算成世界坐标出 JSON，`--mark-out` 出红球复核图                  |
| `pose_render.py`      | 姿态 × 机位带材质渲染；`--sweep-progress` / `--sweep-angle` 逐点给 BVH 距离 + 相交对数并出图（中段 20–40% 才是穿模高发段）                         |
| `bake_deploy_fold.py` | ⭐ 起竖 / 收拢烘焙：折叠角从几何解、逐帧给挂点骨骼打关键帧、绝不归零 `arm.location`、逐帧偏差自校验                                                       |
| `rail_mesh.py`        | 出管挂架网格：抄骨骼世界矩阵 → 建 4 mm `Chassis` → 三角化 → 导出；仰角不符或骨骼不共姿态直接拒绝                                                      |
| `render_ground.py`    | 验收弹体落位：红=实际、绿=应为，判定挂点与几何中心相距应 < 0.01 m                                                                            |

> Blender 需自行安装并用可执行文件的绝对路径调用（不在 PATH；当前环境的示例路径记在 `SKILL.md §6`）。  
> 示例：`blender -b -P split_shells.py -- in.fbx out.fbx --spec parts.json`  
> Blender 里**相对输出路径会掉到盘符根**（`out/x.png` → `C:\out\x.png`），自写脚本时须转绝对路径。

### 4.3 运行环境的硬规矩

- **绝对不要内联执行 Python**（bash 吞反斜杠、缺 `ls` / `head` / `tail`）：写成 `.py` 文件再跑。
- 查询优先用现成的 `recon.py` / `ndfq.py`，别手写一次性脚本。

## 5. 给智能体的执行清单

### 5.1 前置检查：动手前必须答完 5 + 1 问

| #   | 问题                   | 答不上怎么办               |
| --- | -------------------- | -------------------- |
| 1   | 克隆源是什么形态？            | 回去跑 `00-recon.md` 勘查 |
| 2   | 单位落在哪个栏？             | 同上                   |
| 3   | 有没有武器 / 乘员？          | 同上                   |
| 4   | 独立购买还是靠运输？           | 同上                   |
| 5   | 原版有没有同类先例？           | 同上                   |
| 6 ⭐ | **这个部件在模型上的具体位置在哪？** | **直接问用户，不要猜**        |

第 6 问专属于「炮口 / 挂点 / 舱门 / 传感器」这类定位。规矩见 `SKILL.md §3` 铁律 12 与 `23-mesh-import.md §5.0`：  
**给一张叠了 A–T / 1–16 网格的同角度渲染图，让用户报格子**，不要拿自己猜的答案问「是不是这里」；用户已标注过的默认标注正确；一次只问一个判据。

### 5.2 顺序表（不要跳步）

```
1 查   只读勘查 → 确定改哪个文件、字段怎么填、枚举有哪些值
2 判   RTTI 三方对比 → 判断引擎能力边界；「原版 0 先例」只能进待验清单
3 问   只有用户知道的事实，先问再动手（尤其是模型位置）
4 改   探测换行/编码 → 备份 → 按块切片写入 → 锚点链式递进 → 只读守卫校验
5 编   genmod_guard.py（不看退出码，看弹窗解析与「Mod Generation Success」）
6 验   按依赖顺序：买得到 → 存得住 → 名字对 → 模型对 → 有人 → 打得出 → 有火光 → 看画面
7 退   出问题按 manifest 回滚，绝不手工按块删
```

### 5.3 禁止动作

改现有弹药对象 / 改现有 `WeaponDescriptor` 的 `Ammunition` 指向 / 共享载具 depiction / 沿用克隆源 `Name` token /  
拿「原版 0 先例」当「引擎不支持」/ 用退出码判成功 / 游戏开着时编译 /  
手改 `Generated/UserInterface/`（那是 FileWriter 生成的桥表，下次编译会被覆盖，要改上游）。

### 5.4 文档写法约定

每个改动点按 **【原理】→【操作】→【验收】** 三段写；  
知识文件末尾设「给智能体的执行清单」（前置检查 / 顺序表 / 禁止动作）与「定稿参数总表」；  
结论一律标 **【实测】** 或 **【推断】**，推断项进「待验清单」，不能当结论交付。  
验证完成后，待验计划要回写为已验证手册，**并显式列出被推翻的判断与错因**——错因比正确答案更有价值。

## 7. 仓库约定

- **换行统一 LF**：`.gitattributes` 强制 `*.md` / `*.py` 等文本 `eol=lf`。原因：这些文件会被拷回 skills 目录直接使用，Windows 全局 `core.autocrlf=true` 会把工作区改成 CRLF，导致每次同步产生全文件假 diff。常见二进制后缀（`.png` / `.ndfbin` / `.tgv` / `.fbx` …）已标 `binary`。
- **忽略规则**：`__pycache__/`、`*.pyc`、`.venv/`、`.workbuddy/tmp/`、`*.log`、`*.bak`、`out/` `build/` `dist/`、编辑器与系统杂项。
- **可移植性**：正文里的路径均为示例，不是硬编码依赖；换环境时按 `SKILL.md §6` 的说明调整 Python、Blender 与 Mods 目录位置。
