# 高抛 / 曲射弹道调参：先在设计器里试算，再回写 NDF

**本文件管**：导弹飞行剖面的**形状**——爬多高、在哪压平、平飞多长、末段怎么下去、落点在哪。
以及那条铁律：**凡涉及弹道形状的需求，先让用户在设计器里手动试算，参数确认后再动 NDF。**

**不管**：
- 弹道类型能不能选、`GuidedMissile` vs `Obus` 的判据、挂架链、出管方向 → `26-ground-missile-tel.md`
- 弹药总弹量、齐射数、伤害字段 → `22-ammo.md`
- 面板上显示的射程/速度数字 → `60-numbers.md`

> 工具：`scripts/warno_loft_designer.html`（单文件、零依赖、双击即用）。
> 它**不是引擎模拟器**，是「同一套几何算法 + 可视化」的试算台；
> 引擎里真正怎么飞仍以实机为准（见 §6）。
>
> 维护提示：这份 HTML 是**分发副本**，它的开发源另有一份配套的无浏览器回归脚本
> （194 项断言，含历史口径逐位复核）。改动后要**重新拷贝**到 `scripts/`，否则两边会分叉。

## 0. 什么时候必须上这个工具

**【原理】** 弹道形状由 13 个字段耦合决定，**改一个会牵动其余**：
速度律决定曲率半径（`R = v/ω`），`R` 决定能爬多高，能爬多高决定会不会冲过巡航线，
冲过去之后末段下压角的起点又变了。在 NDF 里盲改一个数、编译、进游戏看，一轮 3–5 分钟，而且
**看不出中间量**（当前 α 是多少、相切点落在哪、末段够不够距离）。

**【操作】** 出现下面任一条，**先开工具**，不要直接改 NDF：

| 用户说 | 工具里要看什么 |
|---|---|
| 「飞得太高 / 像抛石机 / 不够高」 | `CruiseAltitudeGRU` = H，看是「梯形」还是「抛物线」 |
| 「一起飞就压平 / 没爬升段」 | `h_arc(88.5°)` 与 ΔH 的关系，是不是退化成保持段 |
| 「打不远 / 落点比瞄准点远」 | 超调量 + 末段落点卡片 |
| 「末段太陡 / 太浅 / 直接砸下来」 | 末段触发距离 `Dt` 与 `Terminal.AutoGyr` |
| 「平飞段太长 / 没有平飞段」 | 平飞段是**余数**，看卡片里的「平飞段」长度 |
| 「改加速度没反应 / 改角速度没反应」 | 转向率归属（`unified`/`split`）+ 速度律，见 §5 |

**【验收】** 工具里能画出与用户描述同形状的曲线，才算「理解了他的需求」；
画不出来就先问，不要进下一步。

## 1. 打开与预设

**【操作】**

```bash
# Windows
start "" "<skill>/scripts/warno_loft_designer.html"
```

`<skill>` 通常是 `C:\Users\<你>\.workbuddy\skills\warno-modding`。
也可以直接把这个路径丢给用户让他双击——**单文件、无依赖、不联网**。

内置两个预设，都是实测参数：

| 预设 | 用途 |
|---|---|
| **AGM114A** | 原版唯一的高抛实例族。H=141、无平飞段，近似抛物线，短射程 |
| **SRBM** | 40 km 级弹道导弹（H=5000、Dt=8000）。有爬升段、保持段、长平飞段 |

**【操作】** 选与目标**形态最接近**的那个，再逐字段改成目标弹的真实参数——
不要从「自定义」空白起步，也不要跨形态硬套（把 AGM114A 的参数按 SRBM 的 D 去用，
会得到一条不存在的弹道）。

**【验收】** 预设选中后曲线立刻出现，且右上角形状标签（抛物线 / 梯形 / 巡航高度超调）与预期一致。

## 2. 参数栏 ↔ NDF 字段映射

**【原理】** 工具里有两类数：**能填进 NDF 的**，和**由几何派生的**。
把派生量当字段写进 NDF，编译不会报错，但**什么都不会发生**。

### 2.1 填得进 NDF 的（13 个）

| 工具字段 | NDF 字段 | 备注 |
|---|---|---|
| 巡航高度 `H` | `TGuidedMissileMovementModuleDescriptor.CruiseAltitudeGRU` | 决定「梯形」还是「抛物线」 |
| 末段触发距离 `Dt` | `HorizontalDistanceToTargetToStartTerminalPhaseGRU` | 决定末段有多长、够不够压下来 |
| 爬升段速度 `va` | `AscendantPhaseConfig.MaxSpeedGRU` | |
| 末段速度 `vt` | `TerminalPhaseConfig.MaxSpeedGRU` | 通常是三段里最快的 |
| 平飞速度 `vc` | `DefaultConfig.MaxSpeedGRU` | ⚠ **必须等于** `Ammunition.ProjectileSpeedGRU` |
| 平飞 AutoGyr | `DefaultConfig.AutoGyr` | `unified` 口径下**不参与上升段**，见 §5 |
| 失控段 AutoGyr | `UncontrollableConfig.AutoGyr` | |
| 上升段 AutoGyr ★ | `AscendantPhaseConfig.AutoGyr` | 实机：**拉起弧与改平弧两段都随它变缓** |
| 末段 AutoGyr ★ | `TerminalPhaseConfig.AutoGyr` | 决定末段能压多快、落点偏多远 |
| Default 加速度 | `DefaultConfig.MaxAccelerationGRU` | 决定平飞段/改平弧的速度律 |
| Ascendant 加速度 | `AscendantPhaseConfig.MaxAccelerationGRU` | **改形状**，不是只改时间 |
| Terminal 加速度 | `TerminalPhaseConfig.MaxAccelerationGRU` | 决定末段转向时的 `R` |
| — | `UncontrollableConfig.MaxSpeedGRU` / `MaxAccelerationGRU` | **当前工具不建模失控段**（出管后几秒的抖动），按克隆源原样带过去即可 |

角度一律**弧度**（NDF 原生单位）。工具里蓝字是度数换算，**导出时只写弧度**。

### 2.2 派生量 / 场景量，**不要**写进 NDF

| 工具字段 | 为什么不能写 |
|---|---|
| `α`（爬升角 / 派生） | 引擎按几何自行解出。写不进去，也没有对应字段 |
| `ω 尺度 k` | 工具侧换算（`实际 ω = AutoGyr × k`），NDF 里只有 `AutoGyr` |
| `v₀`（发射初速） | 实测自静止 = 0；空射/舰射另说，但也不是这个字段 |
| `D`（交战水平距离） | 由武器射程与目标位置决定，不是飞行剖面字段 |
| `h₀` / `hₜ`（发射点/目标高差） | 战场态势，不是单位数据 |
| `θ₀`（发射仰角） | 由发射装置/挂架决定，见 `26-ground-missile-tel.md §4` |
| 速度律 / 闭环 / 转向率归属 / 末段制导 | 工具的**口径开关**，用来在几种假设之间对照 |

**【验收】** 导出的 NDF 片段里**只出现** §2.1 那 13 个字段；
如果看到 `α`、`k`、`v0` 之类，说明导出被改坏了。

## 3. 标准流程 8 步

```
① 取现状  → ② 选预设 → ③ 复现现状 → ④ 定目标形态
   → ⑤ 单变量迭代 → ⑥ 定稿 → ⑦ 导出片段 → ⑧ 回写 NDF
```

**【操作】**

1. **取现状**：用 `scripts/ndfq.py` 把这个弹的四段 config 全读出来。缺一项就问用户，
   不要用工具的默认值顶替（工具的默认值是 SRBM 的，不是他的）。
2. **选预设**：见 §1。
3. **复现现状**：把真实参数填进去，看画出来的形状**是不是他描述的现在这个形状**。
   - 一致 ⇒ 模型对他的弹有效，可以往下调。
   - 不一致 ⇒ **先停下来**，让用户补一条观察（哪一段不对），见 §6。
4. **定目标形态**：把「再高一点」「不要平飞」这类模糊话翻译成 1–2 个数（`H`、`Dt`），
   让用户确认。**不要自己替他决定射程与高度。**
5. **单变量迭代**：一次只改一个字段，记下曲线与卡片变化。工具的「预设」可随时回退。
   - 先定 `H`（决定形态）→ 再定 `Dt`（决定末段）→ 最后微调三个 `AutoGyr` / 三个加速度。
6. **定稿**：把 §8 那张表填满，逐项跟用户过一遍。
7. **取片段**：点工具里的 **「复制 NDF 片段」**，得到只含官方字段的片段
   （头部有 v6.6 注释、弧度/度数对照、以及那条硬约束提醒）。
8. **回写 NDF**：**逐字节克隆现成导弹**，只替换这 13 个数，不要手写整个块
   （见 `26-ground-missile-tel.md §2` 的【操作】）；改完先跑 `genmod_guard.py`。

**【验收】** 编译 `rc=0`（且弹窗通道无原文）→ 进游戏飞一次 → 与工具图逐段对照（§6）。

## 4. 诊断怎么读

**【原理】** 工具会把「几何上已经装不下 / 已经冲过去」的情况显式报出来，
这些正是纯看 NDF 看不出来的东西。

| 诊断 | 含义 | 怎么处理 |
|---|---|---|
| 🔴 **巡航高度超调 +N m** | 上升段 ω 太低或 `H` 太低，压到水平前已经冲过巡航线 | 提高 `H`、提高 `Ascendant.AutoGyr`、或降低 `va` |
| 🔴 **末段来不及对准** | 从当前高度与速度、以 `Terminal.AutoGyr` 压不下来，头会先飞过目标 | 提高 `Dt`、提高 `Terminal.AutoGyr`、降低 `vt` |
| 🔴 **末段落空 / 未穿越目标高度线** | 一直没压到目标高度，轨迹飞出画面 | 同上，先看末段 R |
| 🟡 **本段没加速到位** | 段太短，速度没到本段 `MaxSpeedGRU` | 正常现象，确认可接受即可 |
| 🟡 **早触发** | 触发距离大于可用水平距离 | 调 `Dt` 或射程 |
| 🟡 **近垂直发射** | `θ₀` 接近 90° | 正常（高抛本就这样），但要检查拉起弧是否退化为 0 |
| 🟡 **斜直线被压成 0** | 两段转向弧已经装下 ΔH，没有保持段 | 说明是「抛物线」，不是「梯形」——确认这是不是要的形状 |

**【操作】** 红项**必须先处理或明确接受**，再往下走；黄项在交付说明里写一句就行。

**【验收】** 工具里无红色告警，或每条红项都有用户确认过的理由。

## 5. 已知口径与未定项（重要：别把标定值当实测值）

**【原理】** 工具里有三个「口径开关」，对应三条**尚未被实机定死**的假设。
它们默认取当前最自洽的一支，但**都不是 NDF 事实**：

| 开关 | 默认 | 含义 | 状态 |
|---|---|---|---|
| 速度律 | 按加速度变速 | 段内速度按 `MaxAccelerationGRU` 变化 ⇒ `R=v/ω` 逐点变 | 实机：加速度**会**改形态。切 `const` 可复现旧口径 |
| 转向率归属 | `unified`（上升段统一 `gAsc`） | 拉起弧与改平弧共用 `Ascendant.AutoGyr` | 实机：调低它**两段都变缓**。切 `split` 为旧分相口径 |
| 末段制导 | `closed`（闭环追踪） | 每步朝目标转，转角受 `Terminal.AutoGyr` 限幅；落点可 `<D / ≈D / >D` | 实机：超调后**仍会**在 ω 允许范围内修俯角。切 `fixed` 为旧「冻结下压角」口径 |
| **ω 尺度 `k`** | **1.5** | `实际 ω = AutoGyr(rad) × k` | ⚠ **标定值，不是实测值**。改回 1.00 可复现早期基线 |

**【操作】**
- 交付时若用户拿**早期资料**（k=1.00 口径）的数字对照，让他把 `k` 调回 1.00 再比——
  否则所有 `R`、`L_asc`、`α` 都会差 1.5 倍，看起来像工具错了。
- `GRU ≈ m` 是**假设**。真实换算若不同，所有长度等比缩放，**形状不变**。
- **末段/平飞是否也共用同一个 ω 尚未实测**：当前末段独立读 `Terminal.AutoGyr`。
  若实机发现改 `Terminal.AutoGyr` 连带改了上升段，才需要四段统一。
- 工具里还有个 **「按预算反解 k」** 按钮：它反解的是「让爬升段相切点正好落在 `D − Dt` 预算内」
  所需的那一个 `k`。那是**拟合值**，用来回答「要多大转向率才装得下这个射程」，
  **不是**标定结论，别把反解结果写进交付说明当实测。

**【验收】** 任何写进交付说明的数字，都要能说清它是在哪套口径下算的。

## 6. 实机验收：工具与实机不一致时，改工具不改 NDF

**【原理】** 工具是**推断模型**，实机是**事实**。两者冲突时，只有一种正确处理：
把实机观察当成新证据，回头改模型，**而不是**把实机结果解释成「模型没错」。

**【操作】** 实机飞一次，取**俯视 + 侧视**同帧录像，按下面顺序比：

| 比什么 | 怎么比 | 不一致说明什么 |
|---|---|---|
| 有没有斜直线平台 | 侧视看俯仰角是否有一段严格恒定 | 没有 ⇒ `k` 远小于 1.5，或 `H` 太低 |
| 压平点水平距离 | 侧视/俯视对照地面网格 | 差得多 ⇒ `k` 或 `GRU≈m` 有问题 |
| 实际巡航高度 | 侧视读最高平飞段的高度 | 高于设定 ⇒ 超调工况，或 `Ascendant.AutoGyr` 太低 |
| 末段下压角是否变化 | 逐帧看俯角 | 变了 ⇒ 闭环口径对；不变 ⇒ 才回到 `fixed` |
| 落点相对目标 | 俯视看爆点与瞄准点 | 远了 ⇒ 末段 ω 不够，属正常；**绕回来再打中**才有额外机制 |

**【验收】** 至少「形状（梯形/抛物线）」与「压平点大致位置」两项对上，才算模型可用；
单项对不上就记下来、问用户，**不要靠调 `k` 硬凑**（`k` 一改全盘皆变，会把别的结论一起带偏）。

## 7. 给智能体的执行清单

> **角色分工（重要）**：**用户**在工具里拖参数——只有他知道「这条曲线像不像他要的」；
> **你**负责读 NDF 现状、把初值填好、解释红/黄诊断、把「再高一点」翻译成具体数字、最后把定稿的 13 个数写进 NDF。
> 不要自己算完就动手，也不要替用户决定射程与高度——这两项是他的战术意图。

### 前置检查（缺一条就别动手）

- [ ] 弹药在 `Gfx/AmmunitionMissiles.ndf`、`ProjectileType = GuidedMissile`（否则是炮弹，工具帮不上）
- [ ] `MissileDescriptors.ndf` 里有对应飞行实体与四段 config
- [ ] 已用 `ndfq.py` 读到**现状全部 13 个参数**（读不到就问用户，不要填默认值）
- [ ] 已知目标交战距离 `D`（射程）与期望形态（抛物线 / 梯形 / 高抛）
- [ ] 用户已同意「先试算、后落实」这条流程

### 顺序表

| # | 动作 | 判据 |
|---|---|---|
| 1 | 把 `scripts/warno_loft_designer.html` 交给用户双击打开（或本地开预览） | 能画出曲线 |
| 2 | 选最接近的预设（AGM114A / SRBM） | 形状标签与预期同类 |
| 3 | 填入现状参数，复现「现在的形状」 | 与用户描述一致 |
| 4 | 把目标形态翻译成 `H` / `Dt` 两个数，请用户确认 | 用户点头 |
| 5 | 单变量迭代，每次记下曲线与红/黄诊断 | 无未处理红项 |
| 6 | 填满 §8 定稿表，逐项过一遍 | 用户确认全部数值 |
| 7 | 点「复制 NDF 片段」→ 逐字节克隆回写 | 片段只含官方字段 |
| 8 | `genmod_guard.py` 编译 | `rc=0`，弹窗通道无原文 |
| 9 | 实机飞一次，按 §6 五项对照 | 形状与压平点对上 |

### 禁止动作

- ❌ **跳过工具直接改 NDF**（尤其「凭感觉把 `H` 加减一千」）
- ❌ 把 `α` / `k` / `v₀` 当字段写进 NDF
- ❌ 改 `DefaultConfig.MaxSpeedGRU` 却不改 `Ammunition.ProjectileSpeedGRU`（硬约束，必须相等）
- ❌ 把工具给的绝对落点当实机落点用（末段 ω 归属未实测，数值只作定性）
- ❌ 靠调 `k` 去凑实机数字（会把所有 `R` 与 `α` 一起带偏）
- ❌ 拿「抛物线」当唯一正确形状（有平飞段的梯形同样是合法形态）
- ❌ 让用户先改 NDF、再回来用工具解释结果（顺序反了，等于把工具当验尸工具）
