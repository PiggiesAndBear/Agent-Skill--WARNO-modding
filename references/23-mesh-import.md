# 导入自定义网格（FBX → 战场上的模型）

**本文件管**：把一个外部模型（.blend / .obj / 别的游戏的资产）变成 WARNO 能用的单位网格——
硬约束、锚点契约、七步流水线、锚点定位、NDF 三处接入，以及**按装备类型该接哪些子系统**的清单。
**不管**：拆件/枢轴/炮塔/履带/旋翼/起落架（`24-rig-parts.md`）、材质与导出细节（`25-asset-pipeline.md`）、
depiction 注册（`21-depiction.md`）。

## 0. 判据：什么时候走这条路

| 情形 | 走哪条 |
|---|---|
| 只是换涂装 / 换编号 / 换个型号名 | 克隆官方网格，**不要自建** |
| 复用官方模型，只改 depiction 引用 | `21-depiction.md`，本文不看 |
| **手上是一个外部模型**（.blend / .obj / 其它游戏的资产） | **本文** |

一句话结论：**外部模型能进 WARNO，但代价不在「格式转换」，在「把引擎要的名字补齐」。**
格式上只要 ≤ 65,536 顶点、UV 在 ±4 内、FBX 二进制 7.x，AssetCooker 就会吃；
真正的坑是**空物体名字**——缺失不报错，直接 CTD。

## 1. 硬约束总表

| 项 | 要求 | 违反的后果 | 依据 |
|---|---|---|---|
| 顶点数 | **≤ 65,536** | 烘焙/加载失败 | 手册 + 实测 7,572 |
| 三角面 | 参考官方 Mi-24V 约 4.1 万 / 官方 M1 坦克 1.2 万；**1.5 万已足够** | 无硬限，只影响帧率与 Koch 时间 | 实测 15,103 / 11,914 |
| 根网格名 | **`Chassis`** | 白模 / 不被识别为单位网格 | 引擎硬规则 |
| UV | **必须落在 [−4, 4]** | `AssetCooker` **fatal**：`[mesh.neu3] Can't quantize texcoords…UV=(142.87, -13.6)` | 实测 |
| 材质数 | 少而精。**多材质可用**：官方 `M1_Abrams` 用 4 个材质（车体/炮塔/左右履带/机枪）+ 41 个网格 | 98 个材质无法合批 | 实测 M1 |
| 贴图 | 与 `.fbx` **同目录**，每套 5~6 张：`<名>.png` `_M` `_R` `_NM` `_O` `_A`。**可多套并列**（M1 有 `M1_Abrams` / `M1_Abrams_tracks` / `M240_tank` 三套）。**关键：`_R`/`_M`/`_NM` 必须在材质里各挂一个 Image Texture 节点**（见 `25-asset-pipeline.md §2`）；只挂 base color，等于其余通道全部无效 | 表面发油发亮（默认材质），编译产物缺 `TSCNM` / `TSCORM` | 实测 T-90A |
| 节点类型 | 网格 `Mesh` + 锚点 `Null` | 锚点做成 Mesh 会多出实体 | 实测 |
| 朝向 | **机头 / 车头朝 +X** | 单位倒着飞 | 官方 Mi-24V：机头炮口 x=+7.03；M1 炮口 x=+5.5 |
| FBX 版本 | 二进制 **7.x**（7400 可用） | — | 实测 |

> ⚠ UV 是唯一会**明确报错**的几何项，其余都是静默失败。所以「编译 fatal」先查 UV，
> 「编译过了但画面不对」先查名字。

## 2. 【原理】锚点 = 空物体名字，硬校验

引擎不读骨骼蒙皮权重，它按**节点名字**驱动一切：特效从哪冒出来、炮塔绕哪根轴转、
旋翼绑在哪、飞行员贴在哪。这些字段全部是字符串：

| 字段 | 在哪个对象 | 指向 |
|---|---|---|
| `Anchors = [ 'fx_tourelle1_tir_01' ]` | `DepictionOperator_WeaponInstantFire` | 开火点 |
| `ZAxisNode` / `YAxisNode` | `TCosmeticTurretOperatorDesc` | 炮塔旋转轴 |
| `HelixBoneName` / `BladesBoneName` | `DepictionOperator_Rotors` | 旋翼中心 / 桨叶 |
| `Anchors`（子描绘） | `DepictionOperator_*` 挂乘员 / 外挂网格 | 飞行员、挂件 |

**校验发生在加载时，不是编译时。** 名字对不上 = `Fatal error` + 12 条缺失清单 + CTD。
编译永远 `rc=0`、`Mesh_All.spk` 也照常变大，看不出问题。

### 2.1 官方模型的真实层级（实测 Mi-24V，非文档）

```
Chassis [Mesh]
├─ Tourelle_01 [Mesh]        ← 有机炮塔几何
│   └─ Axe_Canon_01 [Mesh]   ← 俯仰轴
│       └─ Canon_01 [Mesh]   ← 炮管
│           └─ Fx_Tourelle1_Tir_01 [Null]   ★ 开火锚点在炮管末端
├─ Tourelle_02 [Null]        ← 纯旋转节点，无几何
│   └─ Axe_Canon_02 [Null]
│       └─ Canon_02 [Null]
│           ├─ fx_tourelle2_tir_01..04 [Null]
│           └─ AS_1_1..4 / AS_2_1..4 [Null]  ← 挂架（AS 兼容对空/对地；N 是武器序号，
│                                              必须从 1 连号，与 WeaponIndex 无关，见 24 §7.1）
└─ Bloc_Moteur_1 [Mesh]
    ├─ FX_Helice_HS_1 [Null]
    └─ Helice_LS_1 [Mesh]
```

**两条推论，直接决定摆法：**

1. **会追瞄的炮塔，开火锚点必须挂在 `axe_canon_0N` 之下。** 挂在 `Chassis` 上的锚点是
   世界固定的，炮塔转过去了、炮口特效还留在原地。
2. **不需要转的武器，锚点挂 `Chassis` 就行。** 轨道打击类从天而降，炮口只承担视觉。
   （本项目 SuperDestroyer 的 7 个开火锚点全挂 `Chassis`，实机验收通过。）

> 如果单位用了 `DepictionOperator_Turret_1_Aim` 且模型里 `tourelle_01` 是原点处的空 Null，
> 该算子会**旋转两个看不见的节点**，视觉上等于没有——不报错，容易误以为"炮塔在动"。

### 2.2 名字匹配不区分大小写

官方模型写 `Tourelle_01` / `Pilot` / `Helice_LS_1`，NDF 里写 `'tourelle_01'` / `'pilot'`，
两边都能跑。**统一用小写**，避免同一模型里出现只差大小写的两个名字（谁命中不可预期）。

### 2.3 【铁律】引擎默认算子要的「标准特效骨骼」必须一次配齐

**描绘块里没写、也必须有的名字**：引擎会为每个单位自动挂 18 个默认外观算子
（`TCosmeticSelectionStyleOperatorDesc`、`SpottedStyle`、`ExplodedStyle`、`SetToPose`、
`DamageOperator`、`CadaverBurning`、`TacticGhost` …），它们引用一组固定骨骼。
**少一个就 `Fatal error` + 载入 CTD，而且一次只报第一个**——改一个、再崩一个，能来回七八轮。

> 实测原文（四旋翼无人机首次进游戏）：
> ```
> Can't load 'Glad:/NDF/GFX/Depiction.ndfbin':
> Failed to load object '18 operators': TCosmeticSelectionStyleOperatorDesc … TCosmeticTacticGhostCo[…]
> : Errors on mesh '[high]' in Assets/3D/Units/…/QUADCOPTER_RECO.fbx:
> * Missing anchor bone 'fx_chaleur_01'
> ```
> 报错点在 **FBX** 上（网格缺骨骼），不是 NDF 上——看到 `Can't load …Depiction.ndfbin` 先去查网格节点。

载具/飞机通用的一套（Ka-58、Mi-2 同款，**建议整组照抄**）：

| 骨骼 | 用途 | 摆位建议 |
|---|---|---|
| `Fx_Moteur` | 动力/散热源 | 机身顶中央 |
| `Fx_Chaleur_01` | 热浪（悬停最明显） | 顶面上方 5~10 cm |
| `Fx_Incendie` | 起火点 | 机腹/中段 |
| `Fx_Munition` | 弹药殉爆 | 中段（**无武装也要有**） |
| `Fx_Fumee_01` | 烟 | 顶面偏后 |
| `Fx_Trainee_01` | 拖尾 | 尾部 |
| `Fx_Leurre` / `Fx_Leurre_2` | 干扰弹 | 左右各一 |
| `Fx_Stress_01` / `Fx_Stress_02` | 战损特效 | 机身两侧 |

带乘员的再加 `pilot` / `pilot2`；直升机加 `bloc_moteur_N` / `helice_ls_N`。

**按单位类型追加的骨骼**（同样是"描绘块里没写也要有"，缺了同样 CTD）：

| 单位类型 | 额外必需要 | 说明 |
|---|---|---|
| **飞机型**（`TAirplaneModuleDescriptor`） | `aileron_g` / `aileron_d` / `elevator_g` / `elevator_d` / `rudder_1` / `rudder_2` | 引擎自动挂的 `TCosmeticAirplanePartsOperatorDesc` 按名字硬校验这 6 根。**没有舵面的机体（四旋翼无人机）也必须给**，做成无子网格的空物体即可——没有几何就不会有可见动作 |
| 直升机型 | `bloc_moteur_N` / `helice_ls_N` | 见 `24-rig-parts.md §6` |

> 实测：FPV 四旋翼改为飞机型单位后，报的就是 `Missing anchor bone 'aileron_d' / 'aileron_g'`，
> 报错头部的算子列表（19 个默认外观算子）与真因无关，**只看最后那几行 Missing anchor bone**。
全部做成 **Null（空物体）**，父级挂 `Chassis`，**位置只影响特效出生点**，不参与碰撞。

| `fx_fumee_chenille_g1` / `_d1` | 履带扬尘 | 尾轮两侧 |
| `fx_fumee_roue_g1` / `_d1` | 车轮扬尘 | 首轮两侧 |
| `roue_gauche_01` / `roue_droite_01` | 车轮**弹射道具**锚点 | 首轮 |

合计 **21 项**。

> ⚠ **两套轮子命名别混**，这是本项目最容易搞错的一处：
> | 名字 | 作用 | 谁读它 |
> |---|---|---|
> | `roue_elev_{g\|d}{n}`（如 `roue_elev_d1`） | **轮心空物体**，轮子网格是它的子节点，驱动滚动 | 引擎推进算子，见 `24-rig-parts.md §4` |
> | `roue_gauche_01` / `roue_droite_01` | **弹射道具**（`EjectableProps_Vehicle`）出生点，只是特效 | 外观算子 |
>
> 前者有几个轮子写几个（圆点 3 轮/侧 → `roue_elev_d1..3`；长矛 7 轮/侧 → `..1..7`），
> 后者固定 `_01` 一个。把两者当成同一件事，结果就是"轮子不转"或"溅射道具从奇怪的地方飞出去"。

> **口径说明**：项目文档 `TOCHKA_MODEL_HEALTHCHECK.md §4 步 7b` 的标题与验收行写「23 项」，
> 但那张表实际列出 **21 项**，`build_bones_wheels.py` 的 `BONES` 列表也是 21 项。
> 以 **21 项**为准，`23` 是笔误。

**怎么验补全了没有**（两条都要，缺一条就可能"FBX 有名字、baf 没节点"）：

```bash
# ① FBX 侧：名字必须全部命中（不依赖 Blender，秒级）
python fbx_anchors.py check <rig.fbx> \
    --need chassis,tourelle_01,axe_canon_01,tourelle_02,tourelle_03,axe_canon_02,\
fx_tourelle1_tir_01,fx_tourelle5_tir_01,fx_tourelle5_tir_02,fx_stress_01,fx_stress_02,\
fx_munition,fx_moteur,fx_incendie,fx_chaleur_01,fx_fumee_chenille_g1,fx_fumee_chenille_d1,\
fx_fumee_roue_g1,fx_fumee_roue_d1,roue_gauche_01,roue_droite_01

# ② baf 侧：补了 N 项，节点块数应涨 N（本项目实测 19 → 40）
python fbx_anchors.py baf <gen>/.../*_fold.baf --expect-nodes 40
```

> **别用 `count('fx_moteur')` 当判据**：`.neu3` / `.baf` 的字符串池用共享前后缀，
> 命中数会得 0。判据只有「节点块数按新增数量上涨」。

## 3. 【操作】锚点名字从哪来：正向枚举，不许照抄

克隆源换了，锚点清单就换。**照抄别的模型的骨骼名是 CTD 的最常见来源。**

枚举顺序（沿描绘链正向走，缺哪段就补哪段）：

1. 单位块 → `Depiction` 指向哪个 `TacticAerialDepictionRegistration` / `Tactic*Registration`
2. 该注册块的 `Operators` 列表 → 每个算子展开找 `Anchors` / `ZAxisNode` / `YAxisNode` / `*BoneName`
3. `SubDepictions` + `SubDepictionGenerators` → 里面还有一层 `Anchors`
4. `Alternatives` → `MeshDescriptor` → `TResourceMesh`（只关心网格，不出名字）
5. 全部收进一张表，去重，就是 FBX 必须有的节点名全集

> 已知的唯一可靠"抄"法：抄**同一个克隆源**的清单。换源就要重枚举。
> 本项目 SuperDestroyer 以 Mi-24K 为克隆源，得到 10 个强制名字：
> `tourelle_01`、`axe_canon_01`、`as_2_1`、`as_2_2`、`pilot`、`pilot2`、
> `bloc_moteur_1`、`bloc_moteur_2`、`helice_ls_1`、`helice_ls_2`。

### 3.0 用脚本枚举（别手工翻）

```bash
# 1) 沿描绘链收名字，直接产出 need 清单
python scripts/depiction_anchors.py "<Mod>/GameData/Generated/.../DepictionAerialUnits.ndf" \
       --key SE_SuperDestroyer_US --out names.txt --verbose

# 2) 拿清单去校验 FBX
python scripts/fbx_anchors.py check "<资产>/X.fbx" --need-file names.txt
```

`depiction_anchors.py` 会自己跨文件找算子定义（`ZAxisNode` / `YAxisNode` 那批共享算子
在 `Gameplay/Gfx/Units/DepictionOperators.ndf`，不在 Depictions 目录），并递归
Operators / SubDepictions。`--verbose` 会标出每个名字出自哪个字段、哪个块，便于复核。

**它会跳过注释掉的算子**（NDF 里 `// Op_X is ...` 不参与编译，引擎确实读不到），
所以"清单里少了一对锚点"往往意味着**那门武器的算子还注释着**——这是信号，不是 bug。

> 已知盲区：`--key` 只从**一个** depiction 注册块出发。若单位还挂了
> Showroom / Ghost 注册块里有额外锚点，要再跑一次 `--object` 那几个块。

### 3.1 带网格的强制节点要"藏"，不能省

`as_2_1` / `as_2_2` / `pilot` / `pilot2` 这四类会在**该位置生成克隆源的部件**——
米-24 的下颌炮塔和飞行员。两种处理，选一种：

- **把名字留着、位置压进船体内部**：船壳完全遮住，但节点仍在（引擎找得到，不 CTD）；
- **删掉对应子描绘**：更彻底，但 `as_2_*` 若同时是开火锚点会连带失去特效。

> 本项目实际走了「先藏、后删」两步：M26 把它们压进体内，M28 发现删掉子描绘更干净
> （`as_2_*` 会渲染两个米-24 炮塔），于是删了 `as_2_1/2` 两条子描绘、**保留同名 Null 节点**。
> 保留节点是必须的——引擎按名找，找不到就 CTD，与"是否实例化挂件"无关。

## 4. 【操作】七步流水线

> 脚本模板：`mesh_probe/build_destroyer.py`（Blender 后台执行）。
> 调用：`blender --background --factory-startup --python build_destroyer.py -- <输入.blend> <mod内资产目录>`

| 步 | 做什么 | 为什么必须 |
|---|---|---|
| 1 | 绕世界 Z **−90°** | 外部模型常是 +Y 朝前，WARNO 要 **+X**。反了就改 +90 |
| 2 | 解父级时**保留世界矩阵**（`matrix_world.copy()` 后再 apply） | 直接 `parent=None` 会丢变换。实测宽度从 117 m 涨到 186 m |
| 3 | 全部网格合并成单一 **`Chassis`** | 多网格单位要各自配 LOD 与 depiction，不划算；`Chassis` 是硬名 |
| 4 | `remove_doubles(0.001)` | 体素重构/布尔运算后有余留重复顶点，焊接后顶点数才准 |
| 5 | 重建 UV：`cube_project(cube_size = 最长边 / 3.5)` | 压到 ±1.75，躲开 ±4 红线。cube_size 1.0 会让 302 m 舰体冲到 142 |
| 6 | 清空旧材质 → 1 个材质 + 6 张同基名贴图 | 外部模型材质动辄上百，无法合批；重构已毁原 UV，贴图必须重配 |
| 7 | 建全部锚点空物体 **+ 可动件的父子关系** → 按 `25-asset-pipeline.md §0` 的参数导出 | 空物体即锚点，缺一个即 CTD；可动件不做父子的，**永远不动** |

> **步 7 是两件事，必须一起做，别拆开：**
> ① 建锚点空物体（`Fx_*` / `AS_*` / `Roue_Elev_*` …）；
> ② **把驱动的网格挂成它的子节点**，`matrix_parent_inverse = Identity`、局部 `location = (0,0,0)`。
>
> 只建空物体、不建父子，是「轮子不转 / 炮塔不跟 / 起落架不动」的第一大原因——**编译、加载全都不报错**，
> 只是不动。BMPT-787 就踩过：`WHEEL_D1..D8` / `WHEEL_G1..G8` 与同名 `Roue_Elev_*` 都挂在 `Chassis` 下，
> 是**兄弟**而不是父子，转空物体时网格纹丝不动。判据与修法见 `24-rig-parts.md §4`。
>
> 自检（10 秒）：随便转一个 `Roue_Elev_*` 30°，看网格包围盒有没有变；没变就是没挂上。

**步 5 的副作用要知道**：`cube_size = 最长边/3.5` 等价于「一张贴图覆盖约 86 m」。
纯色/程序化贴图无感；日后上细节贴图会明显偏疏，届时要提高分辨率或拆 UV 分块
（每块仍须落在 ±4 内）。

### 4.1 减面：碎片壳体必须先体素重构

外部模型（尤其从游戏里扒的）常常是**几万个互不相连的壳体**。直接 `Decimate`
会失效——每个壳体有自己的最低面数下限，ratio 再小也压不下去。

正确顺序：

```
合并 → Voxel Remesh（voxel_size ≈ 0.8 m）→ 表面变连续 → Decimate → 目标面数
```

实测：41,940 个碎片壳体，体素重构后 Decimate 精确压到 14,998 面，20 秒。
`voxel_size` 是精度与面数的唯一旋钮，太大抹细节（本项目把舰腹炮塔基座从 −4.0 抬到 −2.8 m，
见 §5.2），太小则面数爆掉。

## 5. 【操作】锚点定位：先问人，再量壳面

### 5.0 【铁律】位置类事实先问用户，别用渲染反推

**这一节比后面三节加起来重要。**

「这个东西在模型上的哪里」不是几何题，是**领域知识题**。用户知道那是机炮口还是加油探头，
模型文件不知道，包围盒比例不知道，你的渲染图也不知道。**猜错的代价是整轮烘焙 + 编译 + 部署 + 实机验证。**

#### 该问 vs 不该问

| 该问（只有用户知道） | 不该问（自己查得到，问了是浪费对方时间） |
|---|---|
| 这个位置是哪个部件？是炮口还是探头？ | 这个模型有多少顶点？（`mesh_check.py`） |
| 图上红框里那块，对应模型哪个区域？ | 引擎要哪些锚点名？（`depiction_anchors.py`） |
| 你要的是"从这里冒火光"还是"从这里出弹道"？ | 官方 MiG-29 的 `Salves` 是多少？（`ndfq.py`） |
| 这架飞机的挂载，内侧挂重弹还是外侧？ | 这个字段填什么类型？（`dump_engine_types.py` + 手册） |
| 这两份模型（带/不带起落架）分别用在哪？ | 贴图该挂几个通道？（§1 表 + `25 §2`） |

判据一句话：**答案在文件里 = 自己查；答案在你的脑子里 = 问。**

#### 【原理】为什么不能"自己找一个，然后问是不是这里"

拿自己猜的位置去问，问的是**判断题**——用户只能答"不是"，然后你换一个再问。
猜 5 次就是 5 轮对话，而**给一张带网格的全图让用户指，是 1 轮**。
本项目在 MiG-29M 的炮口上正是这样连错三轮（见下），换成点格子法后一轮定案。

#### 【操作】点格子法（一次定案）

工具：`scripts/pick_anchor.py`（Blender 脚本，渲图 / 叠网格 / 反算 / 红球四合一）。

**完整命令序列**（`--cam-json` 是关键：反算时复用渲染时的相机，杜绝手抄错位）

```bash
# ① 渲图 + 叠 A..T / 1..16 网格（--fit 可省掉手算机位）
blender -b -P pick_anchor.py -- render --blend model.blend --out ask_raw.png \
        --cam 12.6,6.2,4.9 --target 7.95,0.75,2.25 --lens 85 --res 2000x1600 --grid 20x16

# ② 用户报格子后反算，同时渲红球复核图
blender -b -P pick_anchor.py -- pick --blend model.blend \
        --cam-json ask_raw.png.cam.json --cell M8:N9 --mark-out mark.png
```

**第 1 步：渲一张"用户能认出来"的图**
必须与用户给的参考图**同视角、同朝向**（同一侧、同俯仰）。视角不对，用户在你的图上找不到他圈的那块。
若参考图是侧视图，就渲正交侧视（`--ortho 20`），别渲 3/4 透视。
不知道机位时先 `--fit`（方位角 `--fit 42`、仰角 `--fit-elev 20`）看一眼整体，再换成同角度。

**第 2 步：叠网格 + 行列标号**（`--grid 20x16`，自动画 A..T / 1..16）
给**整机或整个可疑区域**，不要裁剪到只剩一个小方块（裁太小会让用户失去参照）。
格子够大时加 `--cell-labels`，每格右下角再打一个 `M8` 小标；格子小就别开，会糊。

**第 3 步：只问一句**
> "参考图红框那块，落在这张图的哪个格子？报 2~3 个格子即可（如 `M8–N9`）。"

不要附带"我觉得是这里的另一个可能…"——那是把你的猜测塞回给用户，会污染答案。

**第 4 步：把格子反算成世界坐标**

透视相机不能按像素比例线性换算，必须走**投影反解**：

```
像素 (u,v) + 已知相机（sensor 36 mm / lens / 分辨率 / 位姿）
  → 反投影射线 → 与机体求交 → 世界坐标
```

`pick_anchor.py pick` 两种相机都支持（`--lens` 透视 / `--ortho` 正交），
`--cell M8` 单格 / `--cell M8:N9` 区域取中心 / `--cell M8,M9` 多格 / `--px 1000,800` 直接给像素。
输出 JSON（含 `xyz` / `normal` / 命中的对象名 / 落点均值），可直接喂给后面的烘焙脚本。

**第 5 步：红球复核，把结论摆回给用户看**
`--mark-out mark.png` 会在每个反算点放一颗红球渲同角度图（半径默认 = 场景对角线 × 1%，可 `--mark-radius` 指定）。
复核图默认叠网格，所以用户能直接说"偏左两格"。

> 红球落在**机体内部**时会被挡住看不见——那不是反算错，是点不在表面。换侧面机位再看一次，
> 或把 `--mark-radius` 调大到能露头。
回给用户确认"是不是这里"。

> ⭐ **这一步不是形式主义。** 没有红球复核，你无法知道反算对不对——反算错了会一路错到实机。
> 红球图是**唯一**能让人一眼看出"对了 / 差了半米"的东西。**红球没被用户点头之前，不要烘焙。**

**第 6 步：维度换算**
Blender 源模型常不是 1 单位 = 1 m（本项目 MiG-29M 是 **1 单位 = 0.1 m**），
导出前乘系数；且父链若已带整体抬升（如 `GROUND_Z`），锚点局部 z 要**先减掉**，否则会被重复叠加（`24 §7.2`）。

#### 【反例】本项目连错三轮（留着，别再踩）

| 轮次 | 我做的事 | 结果 |
|---|---|---|
| 1 | 用户给截图 + 红框，我在**−Y 侧**找"伸出来的管子" | 找错舷（机头 +X 时机身左舷其实在 **+Y**），整轮白做 |
| 2 | 用户明说"在加油管下方"，我仍把**加油探头本身**当炮口 | 又错；探头是最显眼的那根管子，炮口在它下面凹进去 |
| 3 | 被用户第三次顶回来才停手，改用网格图 → `M8–N9` → 反算 → 红球复核 | 通过 |

三次错误的共同点：**都是"我自己找 + 自己判断"**，一次都没有在动手前把候选区域摊给用户看。

#### 【验收】提问到位的三条标准

1. 问的是**用户能一句话回答**的问题（报格子 / 说是哪个部件），不是"帮我看看这个模型哪里不对"。
2. 用户答复后，**先出红球图复核**再动烘焙脚本。
3. 一个位置只问一轮。若需要第二轮，说明第一轮给图的方式错了（视角不对 / 没网格 / 区域裁太小），**先修图再问**。

### 5.1 【原理】比例法为什么错

`(x_min + L*fx, y_min + W*fy, z_min + H*fz)` 只在**盒子形状**成立。
楔形舰体、锥形机头这类形状，按比例算出的 y 会落到体外。实测 `fx_tourelle2_tir_01`
曾悬在舷侧 **15 m 空中**。

正确做法：**KDTree 找最近顶点 + 沿外法线外推**。

```python
co, idx, _ = kd.find(want)                      # want = 比例算出的"期望方向"
n = (nmat @ chassis.data.vertices[idx].normal)  # 世界法线
if n.dot(co - center) < 0: n = -n               # 体素网格会翻面，强制朝外
loc = co + n * SURFACE_OUT                      # SURFACE_OUT ≈ 1.5 m
```

### 5.2 内部锚点不要"吸附后内推"

`pilot` / `bloc_moteur_*` / `helice_ls_*` 要藏在船体内。吸附最近面再沿法线内推
**不可靠**——最近面可能是某个薄壳，内推 8 m 仍露在外面（实测）。
直接压到**中轴线上**最稳（实心闭合体，轴线上必被包住），保留 ±30 m 内的横向偏移
以免成对锚点完全重合。

### 5.3 改过网格就必须重新量壳面

**这是本项目最贵的一课。** 原始 506 万顶点模型上量出的炮塔基座 Z 是 −4.0 / −2.8，
但成品经体素重构 + 减面后被抬到 −2.83 / −2.35 / −1.68 / −1.49——**高了 1.2~1.3 m**。
照抄旧值 → 锚点浮在船腹下方的空气里，特效悬空。

规矩：**锚点坐标只在「最终导出的那个网格」上量**。原始模型 / 中间 blend 上的测量值全部作废。
流水线里写成「现场量壳面再外露 0.6 m」的自适应形式，重建模型后不必手改数值。

### 5.4 人体锚点（`pilot` / `driver` / `tireur`）：锚点是**模型原点**，不是座垫面

引擎把子描绘模型**原点对齐到锚点**。人形资产的原点在**脚底**（DCC 惯例，它与步兵落地共用同一套模型），
所以 `pilot` 锚点要放在**脚蹬/舱底前部**，不是座椅坐垫上。

放错的典型症状：**飞行员头（甚至上半身）穿出座舱盖**，而 NDF、骨骼、编译全都正常，只有实机看得见。

【判据】在同一列自上而下打射线，量三个面：

```python
# 从 (x, 0, 30) 向下打，直到打穿机体
hits = [3.346, 2.349, 2.273]   # 座舱盖玻璃顶 / 座椅坐垫面 / 舱底（MiG-29M 实测）
```

正确关系是——**臀部落在坐垫面上、头顶低于玻璃顶**：

```
锚点 z ≈ 坐垫面 - (proxy 臀部到脚底的高度)      例：2.349 - 0.34 = 2.01
头顶   = 锚点 z + proxy 全高                   例：2.01 + 1.32 = 3.33 < 3.35 ✓
```

【怎么验】不要靠目测。用一个**原点在脚、坐姿**的方块人形当 proxy（Ka-58 的 `pilotproxy.py`
就是这个：大腿水平 +X、小腿向下、躯干竖、球头，脚底→头顶 ≈ 1.32 m），放到锚点上，
渲「侧视 + 3/4 + 舱内近景」，玻璃给 alpha≈0.2：

- 臀部应压在坐垫面上，不悬空；
- 头顶应低于玻璃顶 0.05~0.15 m；
- 人不能穿过舱底（脚底低于舱底就是锚点太低了）。

本项目实测：`pilot` 曾写 `(67, 0, 4.2)` → 世界 z **2.391**，**几乎正落在坐垫面 2.349 上**
（等于把脚底放在臀部高度），proxy 头顶 3.711，比玻璃顶 3.350 **高 0.36 m**，实机穿盖。
降到世界 **2.150**（局部 `(67, 0, 1.79)`）后修好。

【反向校准】proxy 与官方模型（如 `VVS_Pilot.fbx`）尺寸未必一致，实机才是终审：
若实机只露"头顶一点"而 proxy 在旧值下穿 0.36 m，说明**真实模型比 proxy 矮约 0.24 m**，
按比例下调即可，不必把 proxy 的测量值当成绝对值照搬。

> 相关：`21-depiction.md §3c` 的 `SubDepictions` 写 `Anchors = ['pilot']` + `Depiction = Pilot_Pilote_*`；
> 官方 `Pilot_Pilote_SOV` → `MeshDescriptor_Pilote_SOV` → `Assets/3D/Units/URSS/Infanterie/VVS_Pilot/VVS_Pilot.fbx`。

## 8. 排错：按现象定位

> 这张表**横跨三个文件**，是唯一一份排错表（不按文件复制，免得两头漂）。
> 「说明」列里写了归属，照 `24-rig-parts.md §x` / `25-asset-pipeline.md §x` 跳过去看原理。

| 现象 | 先查 | 说明 |
|---|---|---|
| **表面发油/发亮，像镀铬或上过漆（编译无报错）** | **材质里 `_R`/`_M`/`_NM` 挂节点没有** | 只挂 base color 时编译产物只有 `TSCColor_*` 两张，缺 `TSCNM`/`TSCORM`。引擎回落默认低粗糙度。见 `25-asset-pipeline.md §2` |
| 同上一半（法线接上了但仍不正常） | 法线图基准 | GLB 拆出的 `_NM` 基准偏 33.7°，必须旋转归正。见 `25-asset-pipeline.md §2` |
| 履带/远处越看越亮 | `_R` 的空白区 | 烘焙 atlas 空白被清成纯黑 = roughness 0，mipmap 平均后变镜面。见 `25-asset-pipeline.md §2` |
| 编译 `fatal: Can't quantize texcoords` | **所有 UV 层** | 报的数值可能和 FBX 里的对不上（见下条），别急着怀疑缓存 |
| 同上，但 UV 明明在 ±4 内 | atlas 内缩系数 | AssetCooker 把单图塞进 atlas 时按 `atlas/子块` 放大 UV，实测 **×1.0767**，真实上限 ≈ **3.7** 而不是 4.0。报 `4.09137` 时 FBX 里其实是 `3.8` |
| `fatal: Mesh contains an abnormal normal ... normal length 0` | 导出前是否**真三角化** | `use_triangles` 不管法线来源；必须在数据结构里三角化 + `dissolve_degenerate` |
| `fatal: No diffuse texture for material 'X'` | 该材质有没有贴图 | 纯 `baseColorFactor` 不行；常量材质也要给一张常量 PNG |
| `fatal: Texture slot 'OpacityTexture' ... does not match '^.*_A$'` | alpha 是否借了 diffuse | 透明度必须来自独立 `<名>_A.png` |
| 同上，但 alpha 图明明存在 | **FBX 是否被 Blender 往返过** | 导入导出会丢掉 `_A` 引用（两个节点都指向 diffuse）。见 `25-asset-pipeline.md §3` |
| `normal length 0` 报的 sub-mesh 你根本没动过 | 是否在成品 FBX 上加过几何 | 往返会冒出新的退化面，必须**全场景**清洗。见 `25-asset-pipeline.md §3` |
| `fatal: File not found : '.../X_L.png'` | 贴图文件名是否等于材质名 | FBX 只记文件名，AssetCooker 按同名去 GameData 找 |
| 加载时 `Fatal error` + 一串名字 | 缺锚点 | 硬校验，缺一个即 CTD；名字清单看报错原文 |
| 白模 | `Alternatives` / `TResourceMesh` | 三档都要存在 |
| 地图上隐形 | 主注册块 / `BlackHoleKey` | 见 `21-depiction.md` |
| 有枪无火 | `Actions` 的 tag + 算子类型 | 尤其 `MissileCarriageFire` 不读 Anchors |
| **部署放下单位瞬间 Fatal：`Mesh 'chassis' requires a bbox on bone`** | 有没有多余的同名 `chassis` 空物体 | bbox 由 `Chassis` **网格**提供；空物体没几何 → 取不到 bbox。见 `26-ground-missile-tel.md §3` |
| 加载 Fatal：`Skeleton mismatch between mesh and animation`（N vs N+k 骨） | 动画是否在**最后一次加骨之后**重烘 | 加/删任何骨骼或空物体都必须重烘 deploy/fold。见 `26-ground-missile-tel.md §4.7` |
| **导弹水平出管 / 不沿发射架、朝天乱窜** | `MissileCarriage` 指向的网格 | 出管 box 不在挂架网格里；要单独做一份无动画的挂架网格，见 `26-ground-missile-tel.md §4` |
| 车上有弹、军械库里没有 | Showroom 版 `SubGenerators` | 战场与军械库各自注册，见 `26-ground-missile-tel.md §5` |
| 模型倒着/侧着 | 朝向轴 | 改第 1 步 −90 ↔ +90 |
| 尺寸突然变宽 | 解父级没保留世界矩阵 | 用 `matrix_world` |
| 船上有别的模型的零件 | 子描绘 `Anchors` | 克隆源挂件被实例化了，删子描绘或把节点压进体内 |
| 特效浮在体外空中 | 锚点用了比例法 / 旧网格的测量值 | 改 KDTree 壳面吸附，并在**最终网格**上重量 |
| `找不到 Modele_X` | 是否新建了 `.ndf` | 新文件不被加载，追加到已有文件 |
| 枚举结果比预期少几对锚点 | 对应算子是否被注释掉 | 注释掉的算子引擎读不到，清单里自然没有 |
| **坦克开着走，履带不滚** | **材质名里有没有 `Chenille_Gauche` / `Chenille_Droite`** | 引擎按材质名绑履带 shader 滚 UV，NDF 里没有任何开关。左右必须各一个材质。见 `24-rig-parts.md §4` |
| 材质名改对了，履带仍不滚 / 横向滑动 | **UV 的走向轴是不是 V** | 官方 M1 宽度轴 U、走向轴 V；源模型若是 U 走向，要 UV 转置 + 贴图转置（法线图 RG 互换）。见 `24-rig-parts.md §4` |
| 前进时一侧履带反着滚 | **D/G 是按对象名还是按世界 Y 判的** | +Y 是车左、−Y 是车右。按名字分配，装配脚本命名一错就反向，且编译完全正常 |
| **轮子不转** | 轮子是不是**独立网格 + 同名 `Roue_Elev_*` 空物体** | 合并进 `Chassis` 的轮子永远不会转；空物体必须在轮心，网格局部原点为 0。见 `24-rig-parts.md §4` |
| 一旋轮子就飞出去 | 轮子网格的局部原点 | 必须 = 轮心。原点在世界原点时旋转半径 = 整车尺寸 |
| 拆完轮子编译报 `Vertex count 66465 above limit of 65536` | 新网格**有没有继承 `use_smooth`** | 全平面着色 → 导出按面拆顶点。本项目就超了 929 个，继承 smooth 后一次通过。见 `24-rig-parts.md §4` |
| 拆完轮子侧裙板碎成一片塞进轮子 | 是按**面中心**还是按**连通壳体**分组 | 跨数米的大面板，面中心会落进轮子区间。必须整壳判定 |
| 想给轮式卡车做轮子转 | — | 官方轮式样例根本没有 `Roue_*` 节点，轮子旋转只对履带车实现 |
| **拆出来的部件一转就露出内壁** | 是不是按面/按坐标切的 | 三角汤模型必须「焊接 → 连通块 → 整壳归组」，否则接缝开在曲面中间。见 `24-rig-parts.md §1` |
| **拆走某块部件后机身出现空洞** | 它背后是不是机身凹兜 | 单层曲面拆走必露兜。先做「隐藏 + 红底 + 背面剔除」判定。见 `24-rig-parts.md §1` |
| 隐藏部件后原地还有一块"同形灰壳" | 主壳体的凹兜，拆不开 | 该件只能"压平/贴向机体"，不能搬走或大幅旋转。见 `24-rig-parts.md §1` |
| **旋翼/螺旋桨转起来像"歪帽子"、桨盘画圈** | 枢轴是不是抄了骨骼位置 | 骨骼与几何回转中心可能差 0.8 m；用三桨质心求外心。见 `24-rig-parts.md §2` |
| 起落架收起后**穿出座舱 / 从下往外翻** | ①旋转符号 ②角度过大 | 引擎绕 X 方向与 Blender 相反；角度按"投影宽度"算（150° 时轮盘 Y 向 1.26 m）。见 `24-rig-parts.md §5` |
| **改了起落架/舱门角度，进游戏毫无变化** | 有没有重新编译 | 这类 ndf 会进 `Depiction.ndfbin`，不编译不生效且**不报错**。见 `40-engineering.md §5.7` |
| 起落架收放找不到配置（翻遍 depiction 都没有） | 走的是 **CoatingRecipe**，不在 depiction | `DepictionCoatingPantry.ndf` + `DepictionCoatingCookbook.ndf`。见 `24-rig-parts.md §5` |
| 配方写了但不动 | `CoatingName` 是否等于 depiction 的 `BlackHoleKey` | 写错不报错，只是不动。见 `24-rig-parts.md §5` |
| 自建小 FBX 编译报 `No diffuse texture` / `Missing UV indices` | AssetCooker 两道硬门槛 | 材质挂 diffuse（材质名=贴图基名）+ 必须有 UV。见 `25-asset-pipeline.md §6` |

## 9. 验收清单（导入级，按顺序别跳）

- [ ] `fbx_anchors.py check` 通过：`Chassis` 是 Mesh，全部锚点名命中，层级对

## 10. 被推翻的判断（留着，别再踩）

| 曾经的判断 | 实际 | 错因 |
|---|---|---|
| 「履带不滚要去 NDF 里找动画配置 / 得挂 `TAnimatorDescriptor`」（T-90A 轮） | 全库 4368 个 ndf 搜 `Roue`/`Animator` 零命中；`TCosmeticCaterpillarTrackOperatorDesc` 只有 4 个字段、无骨骼或材质参数。真正的开关是**材质名** | 默认「行为一定对应数据配置」，没先去读官方手册的 Mesh 章 |
| 「履带 UV 怎么展都行，反正贴图能对」 （T-90A 轮） | 官方 M1 宽度轴 U / 走向轴 V，本项目源模型正好相反。照搬导致 shader 滚错轴 | 只比了 UV 范围和覆盖率，没测「哪个轴沿走向」。判据要是「同 X 不同 Y 两点，ΔU/ΔV 谁大」 |
| 「轮子只要从车体拆出来就会转」（T-90A 轮） | 还必须有**同名 `Roue_Elev_*` 空物体**在轮心，且网格局部原点为 0 | 把「独立 mesh」当成了「可独立旋转的部件」，漏了引擎的命名契约 |
| 「新网格建好面就行，smooth 是显示设置，跟导出无关」 （T-90A 轮） | 丢 `use_smooth` → 全平面着色 → FBX 按面拆顶点 → 顶点 66465 超 65536，**编译直接失败** | 把 Blender 的着色标记当成纯视觉属性，没意识到它决定导出时的顶点合并 |
| 「拆轮按面中心分就行，反正是按 X 区间切的」（T-90A 轮） | 侧裙板这类跨数米面板的面中心会落进轮子区间，整块裙板被切碎塞进轮子（D4 的 X 跨度 4.71 m） | 用「面」当单元去分区，而几何的自然单元是「连通壳体」 |
| 「模型里没有对应名字的锚点，对应部件就静默不生成，所以算子不用删」 | 引擎对 LOD-High 做**硬校验**，缺一个即 CTD | 把「字段是字符串、看起来可选」当成「缺失可容忍」，没做对照实验 |
| 「按包围盒比例算锚点位置就行」 | 楔形船体上会落到体外 15 m | 把盒子假设套到非盒形几何 |
| 「原始模型上量到的坐标可以直接用」 | 体素重构把壳面抬了 1.2 m | 忘了中间改了网格，坐标随网格变 |
| 「按面中心分区就能把部件拆出来」（Ka-58 旋翼头） | 三角汤模型按面分会把壳切开，转起来露内壁；必须焊接后整壳归组 | 把"面"当成几何单元，实际单元是"焊接后的连通壳" |
| 「骨架里有 `bloc_moteur` 骨骼，枢轴就按它的坐标写」（Ka-58 旋翼） | 骨骼在 (0,−0.55)，几何桨盘中心在 (0.617, 0.001)，差 0.83 m；桨盘绕偏心点画圈 | 把"骨架"当成"几何真值"，没做"静止时看不出、转起来才暴露"的对照 |
| 「起落架收放的配置应该在 depiction 的 Operators 里」（Ka-58） | 完全不在 depiction，走 `TCoatingRecipe`（Pantry + Cookbook） | 默认"外观动画都在 depiction"，没先搜 `TCosmeticLandingGearOperatorDesc` |
| 「`Gameplay/` 下的 ndf 运行时直读，改完即时生效」（Ka-58） | 会被编进 `Depiction.ndfbin`，不编译完全不生效、且不报错；两次"改了没变化"都是没编译 | 用"文件看起来只是数据"推断加载方式，没做 ndfbin 体积/mtime 对照 |
| 「单色 Workbench 渲染里发黑的地方 = 空腔」（Ka-58 整流罩） | 单层曲面的背面本来就发黑；实际是"面板 + 机身凹兜"两层结构 | 用渲染明暗判断拓扑，应该用「隐藏 + 红底」或「射线回打」 |
| 「`24-rig-parts.md §3.2` 证明重建可动炮塔不可行，一律别做」（Ka-58） | 要看拓扑：**舰船**是融合壳、挖洞必露底；**直升机的炮管本来就是凸出件**，只切炮管（机匣留机身）就成功转起来了 | 把一次拓扑特定条件下的失败当成通用结论，没按判据分类 |
| 「改 `Anchors` 就能让所有武器从炮口出来」 | `MissileCarriageFire` 不读 `Anchors` | 没先确认算子类型的取点逻辑 |
| 「切不开就重建：删凸起 + `holes_fill` + 新建独立炮塔」（M29 轮） | 实机整片内部结构暴露，整段回滚 | 单层壳上开洞必然穿透到对侧背面；把「补洞成功（无报错、无开放边）」当成「壳体复原」 |
| 「UV 改小了报错却没变，说明是中间缓存」（T-90A 轮） | 是 atlas 内缩系数，报错值 ≠ FBX 值 | AssetCooker 拿**放大后**的 UV 和 4.0 比，`3.8 → 4.09137`、`3.6 → 4.25761`，两轮数值都不等于文件里的值，据此误判成缓存，白查两轮 |
| 「`use_triangles=True` 就够三角化了」（T-90A 轮） | 它只影响导出，`mesh_smooth_type='FACE'` 仍取原多边形法线 | 把「导出选项」当成「数据已三角化」，没意识到法线的来源是导出前的 n-gon |
| 「UV 只要不超 4 就行，平铺无所谓」（T-90A 轮） | 官方 M1 的 UV 全部在 [0,1]，靠贴图内容重复 | 只盯着「编译能不能过」，没去量官方成品模型的 UV 分布 |
| 「贴图和 fbx 放同目录、文件名对上就够了，不用接材质节点」（T-90A 轮，**代价最大**） | AssetCooker 按**材质里的 Image Texture 节点**决定导出哪些通道；只挂 base color 时，`_R`/`_M`/`_NM` 一张都不进 atlas | 把「文件存在」当成「数据被读取」。当时编译一路成功、贴图也显示正常，只有表面发油这一个软症状，就顺手归因成「源模型贴图偏亮」了 |
| 「贴图基名必须等于材质名」 | 官方 `Chenille_Droite` 材质引用的是 `M1_Abrams_tracks.png` | 从「我这么做能跑通」反推出「这是规则」，没去看官方反例 |
| 「FBX 导入再导出是无损的，节点树一致就说明没丢东西」（T-90A 圆窗轮） | 节点层级和 4 通道材质确实一致，但玻璃的 `_A` 引用**悄悄换成了 diffuse** | 只比对了"节点数量/名字/连线"，没逐张核对 `image.filepath`。**同名 image 被加 `.001` 后缀就是线索** |
| 「只清导入对象、只处理改动过的那一个 mesh 就够了」（T-90A 圆窗轮） | 报错的 sub-mesh 恰恰是没碰过的 `Axe_Canon_02` | 退化面是**往返行为**的产物，与"你改了谁"无关，必须全场景清洗 |
| 「把可见方向数为 0 的面删掉就能无损减面」（T-90A 高清轮，**与 M29 同一类错误**） | 实机**车体漏风**，能看到/看穿内部；边界边 Chassis 7,994 → 30,677 | 又把「单层壳/双层壳」当成了水密体。内衬面从外面打不出线，但它是既存开口的背板；删掉就直通空腔。M29 轮已经记过同一件事，这次换了个包装（可见性判据）就重犯了 |
| 「法线图只要偏角 ≥3° 就该整体旋转归正」（T-90A atlas 重排轮） | 烘焙出来的 `_NM` 被转了 12.3°（gun）/ 9.7°（mg），众数从 `(128,128,255)` 变 `(111,107,252)` | 只看偏角不看**离散度**。真偏置（GLB 拆出的图）离散 0.4~0.6°；烘焙图的多斜面平均出来离散 10.6°、3.3°，是假偏置。判据必须是 `deg ≥ 3 且 离散 ≤ 2°` 才旋转 |

> 通用教训：**"没报错"不是"生效了"**。判断一条推断真假，成本最低的方法是做一次
> 只读实验（渲染标记球 / 解析 FBX / 换一个变量重编译），而不是在文档里找佐证。

## 11. 给智能体的执行清单

**前置检查**（答不上就先去勘查，别写文件）

1. 克隆源是谁？→ 决定强制锚点清单（§3）
2. 源模型顶点数 / 是否碎片壳体？→ 决定要不要体素重构（§4.1）
3. 目标模型原始朝向是 +Y 还是 −X？→ 决定旋转量（§4 步 1）
4. 武器是「从炮口打」还是「从天而降」？→ 决定锚点挂 Chassis 还是挂 `axe_canon`（§2.1）
5. 单位 NDF 里 `Anchors` 引用了哪些名字？→ 这是最终验收清单
6. 贴图从哪来？→ GLB 拆出来的必须做法线基准校正与空白区填充（`25-asset-pipeline.md §2`）
7. ⭐ **要落锚点的那个"位置"确认了吗？**（炮口 / 挂点 / 舱门 / 传感器）
   → 不清楚就**停下来问用户**，用网格图让用户点格子（§5.0）；**红球复核过之前不要烘焙**

**顺序表**

| 阶段 | 动作 | 产出 / 验收 |
|---|---|---|
| 1 | 跑 `depiction_anchors.py --key <Key> --out names.txt` | 名字清单（含出处标注，`--verbose` 复核用） |
| 2 | Blender 流水线 7 步，**每个材质挂 base + `_R` + `_M` + `_NM` 四个节点** | `.fbx` + 6 贴图 + `.blend` |
| 3 | `fbx_anchors.py dump` | 节点树与名字表逐项对照 |
| 4 | `fbx_anchors.py check --need-file names.txt` | 全命中，`rc=0` |
| 5 | 渲染标记球回看 | 球落在结构的正确位置（**别信数值，信画面**） |
| 6 | 改 NDF 三处 → 编译 | `Mod Generation Success` + spk 变大 + **atlas 出 4 个 tgv**（`TSCColor`×2 / `TSCNM` / `TSCORM`） |
| 7 | 进游戏 | §9 清单 |

> 顺序上的死结要先拆开：**先有（克隆来的）depiction 块，才有名字可枚举**。
> 所以现实流程是「克隆 depiction → 枚举 → 建模型 → 按实际炮塔改算子锚点 → 重跑第 1/4 步再验」。

**禁止动作**

- ❌ 照抄别的模型的锚点名（换克隆源必须重枚举）
- ❌ 用原始模型上的坐标当最终值（网格改过就作废）
- ❌ 新建 `.ndf` 文件放网格资源（不被加载）
- ❌ 用 `export X is "路径"` 简写定义 `TResourceMesh`
- ❌ 生成叶骨（`add_leaf_bones=True` 会多出 `_end` 节点）
- ❌ 拿「编译通过」当「锚点齐了」（编译期不校验锚点）
- ❌ 用 `Decimate` 直接压碎片壳体（先体素重构）
- ❌ 只靠 `use_triangles=True` 就以为「已三角化」（法线仍来自原 n-gon）
- ❌ 把 GLB 的 UV 平铺原样搬过来（官方模型的 UV 全在 [0,1]）
- ❌ 保留 GLB 的第 2~4 套 UV 层
- ❌ 用 diffuse 图自己的 alpha 当透明度（必须走独立 `<名>_A.png`）
- ❌ **只给材质挂 base color**（`_R`/`_M`/`_NM` 不会进 atlas，表面会发油）
- ❌ 把 `_R`/`_M`/`_NM` 按 sRGB 加载（必须 Non-Color，否则 roughness 被压暗）
- ❌ 材质节点里引用的文件名与落盘文件名不一致
- ❌ 在 Blender 里导入 FBX 回来查零法线（导入器会重算，查不出来）
- ❌ ⭐ **位置没经用户确认就烘焙**（炮口 / 挂点 / 舱门）——猜错一轮 = 烘焙 + 编译 + 部署 + 实机全白做
- ❌ ⭐ **拿自己猜的位置问"是不是这里"**（判断题式提问），应给带网格的全图让用户指（§5.0）
- ❌ ⭐ 用户已在图上标注，还去别的面/别的零件找（"标注就是答案，先照做"）
